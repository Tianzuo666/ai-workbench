# 需求 Git 与 MR 工作流

先识别用户本次授权到了准备分支、实施、提交、推送还是创建 MR；只执行已授权阶段。存在清楚的既有授权时不重复询问。只读分析、紧急发布修复或采用其他分支策略的任务不套用本流程。

## 输入

- 需求编号、标题、完整需求链接与标题。
- 各独立仓库的路径和目标迭代分支。
- 当前项目的分支、提交、MR 约定及实际获准阶段。
- Assignee、Reviewer 和合并选项：用户或项目已有明确配置时使用，缺少时仅在需要创建 MR 的阶段确认，不写死人员。

个人维护仓库中的 MEMORY.md 可以提供团队习惯，但路径、分支、人员账号和权限需要按当前任务核实。技能独立安装后不依赖原仓库中的记忆文件。

## 准备分支，需相应授权

1. 读取适用规则、工作区状态、当前分支、remotes 与 upstream，保护已有改动。
2. 在确认的迭代分支基础上获取相关远端更新并安全快进。不能安全切换或快进时说明，不 stash/reset 用户改动。
3. 使用项目确认的命名约定。采用个人常用约定时为 `opt-<需求编号>`；分支已存在时先确认基础和内容，不重建覆盖。
4. 核对新分支 upstream，不能误跟踪迭代/发布分支。未经推送授权不因此推送。

## 实施与提交

- 仅实施明确确认的需求范围，非需求文档默认留在业务仓库外。
- 构建、测试、lint、格式化和类型检查仍需独立明确授权；定义验收条件不代表可以运行。
- 提交前人工阅读 diff 和工作区状态，确定暂存范围，排除用户无关改动与秘密；未经提交授权停在可审阅改动。
- 采用个人常用约定时，Commit message 为 `opt-<需求编号> <标题简述>`，否则使用项目约定。不要把所有工作区内容一并 add。

## 推送与 MR，需相应授权

- 推送前核对 remote、分支和提交。采用上述命名时显式推送同名需求分支，例如 `git push -u origin opt-<需求编号>`，随后核对 upstream；不要把示例占位符原样运行。
- 不默认 force push。发现远端历史冲突先报告，不以 lease 参数自动取得改写授权。
- 多仓库分别创建 MR，源为需求分支，目标为各自已确认迭代分支。
- 个人常用 MR 标题与 Commit message 一致，描述为 `需求 URL 《需求完整标题》`，仅链接 URL；其他项目使用其模板。
- 按已确认人员与选项填写 MR；若当前项目不支持删除源分支或 squash，说明差异。
- 创建 MR 不等于批准、合并或部署，不继续执行未授权阶段。

## 交付

逐仓报告实际分支/提交、已执行阶段、MR 链接、验证结果或未运行项、剩余阻塞。没有执行的阶段明确标记，不把准备好的说明说成已提交/已推送。
